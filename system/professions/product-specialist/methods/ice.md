# ICE e quadrante I×E — score de priorização

## Quando usar / quando não

- Use **depois** que existe solução definida: Facilidade só é estimável com solução
  escolhida. Impacto e Confiança podem nascer na definição do problema.
- Não use no intake (ver `moscow.md`) nem como substituto de julgamento — o score informa
  a conversa, não a encerra.

## Estrutura

- **ICE** = Impacto × Confiança × Facilidade (escalas e fórmula exatas são do projeto —
  leia o documento de priorização do projeto, nunca assuma valores).
- **Quadrante I×E** cruza Impacto e Facilidade em 4 ações: fazer já / planejar / depois /
  descartar. Os thresholds de corte são do projeto.
- **Funil completo**: criticidade (MoSCoW) → quadrante → score. Cada camada refina a
  anterior; nenhuma sozinha decide.

## Barra de qualidade

- **Cada dimensão negociada**: proposta + justificativa + aprovação do usuário, uma por
  vez. Score imposto não é priorização, é decreto.
- **Consistência é auditável**: score registrado ≠ produto das dimensões, label ≠
  quadrante calculado, item priorizado sem score — tudo isso é anomalia a reportar, nunca
  a corrigir em silêncio.
- **Thresholds vêm de documento, não de memória**: se o projeto mudou os cortes, a análise
  reflete porque leu, não porque decorou.

## Contrato de output

Dimensões + score + quadrante + justificativa por dimensão. Numa análise de backlog:
ranking (criticidade → quadrante → score decrescente) + lista de anomalias com ação
sugerida — a correção é decisão do usuário.
